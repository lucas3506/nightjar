Monitor crontab jobs

The one-liner

# /etc/crontab or `crontab -e`
0 2 * * * /opt/scripts/backup.sh && curl -fsS -m 10 --retry 5 -o /dev/null https://wzbetaadovfmwgqfspcw.supabase.co/functions/v1/ping/YOUR_TOKEN

Create the check with the same cron expression (0 2 * * *) and the server’s time zone. If the server runs in UTC, use UTC.

Report the exit code and attach output

The one-liner tells you when the job didn’t run or exited non-zero. To know why, send the exit status and the end of the output:

#!/usr/bin/env bash
# /opt/scripts/with-nightjar.sh  <token>  <command...>
URL="https://wzbetaadovfmwgqfspcw.supabase.co/functions/v1/ping/$1"; shift
curl -fsS -m 10 --retry 5 -o /dev/null "$URL/start"
OUTPUT=$("$@" 2>&1); STATUS=$?
printf '%s\n' "$OUTPUT" | tail -n 100 | curl -fsS -m 10 --retry 5 -o /dev/null --data-binary @- "$URL/$STATUS"
exit $STATUS

0 2 * * * /opt/scripts/with-nightjar.sh YOUR_TOKEN /opt/scripts/backup.sh

You now get duration tracking, the real exit code, and the last 100 lines of output in the failure alert.

Crontab pitfalls that Nightjar catches

  • Minimal environment. Cron runs with a tiny PATH and no shell profile. A script that works in your terminal fails with command not found. Use absolute paths or set PATH= at the top of the crontab.
  • Pipelines hide failures. pg_dump db | gzip > out.gz exits 0 even when pg_dump fails. Add set -o pipefail to the script.
  • % is special. In a crontab line, % means newline. Escape it as \% in date +\%F.
  • Output goes nowhere. Without MAILTO and a working mail setup, cron output disappears. Send it to Nightjar instead.
  • Overlapping runs. If a run takes longer than its interval, runs pile up. Wrap the job in flock -n /tmp/job.lock and alert on duration.
  • The crontab got replaced. A deploy or config-management run overwrites the file. Nothing errors, and the job just stops. That’s exactly the silence Nightjar alerts on.
