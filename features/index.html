Nightjar watches the clock for every scheduled task you have, and speaks up only when one of them misses its slot, breaks, drags or hangs.

03 What it catches

Four ways a job goes wrong. One line catches all four.

Uptime monitors check if a server answers. Nightjar checks if the work happened: on time, successfully, and in a reasonable amount of time.

A Missedno ping

It didn't run at all

Reboots, edited crontabs, a disabled scheduler. Nothing to log, because nothing happened.

B Failedexit 1

It ran and broke

Report the exit code and POST the output. The tail of stderr arrives inside the alert.

C Slow PRO> max

It ran three times longer than usual

Ping /start first and every run is timed. Go over the limit and you get a warning.

D Stuck PROno finish

It started and never finished

A deadlock, a hung request, a lock never released. You know while it's still happening.

01Detection

Missed runs

Every check knows when its next ping is due. If it doesn't arrive within the grace period, the check goes down.

Reported failures

Ping /fail or /<exit-code>. Any non-zero exit status marks the run failed and alerts immediately.

Slow runs

Send /start before the work and every run is timed. Set a maximum duration to be warned when a run exceeds it. Pro and Scale.

Stuck runs

A run that started but hasn't finished within its maximum duration alerts while it's still hanging. Pro and Scale.

Recovery notices

When a failing or late check pings successfully again, every channel is told how long it was down.

Grace periods

From one minute to seven days, so a busy night doesn't page anyone for a backup that's eight minutes late.

02Schedules

Simple periods

Every 5 minutes, every 6 hours, once a day, once a week, up to 31 days.

Cron expressions

Standard 5-field syntax, previewed in plain English as you type, with the next three run times shown before you save.

Time zones

Cron schedules are evaluated in any IANA time zone, so daylight-saving changes don't create false alarms.

One alert per incident

One message when a check breaks and one when it recovers. Nothing every minute in between.

03Context

Log excerpts

POST the job's output with the ping. The tail is stored with the run and quoted in failure alerts: 2 KB on Hobby, up to 128 KB on Scale.

Run history

Every ping, failure and state change, with duration, exit code, source IP and user agent.

Thirty-day chart

Successes, failures and incidents per day, with the average duration for each day.

Delivery log

Every alert Nightjar tried to send, and the HTTP status the receiving service answered with.

04Alerts

Slack, Discord, Google Chat

Incoming webhooks, formatted for each app, with a link back to the check.

Telegram

Use your own bot token and chat ID. Messages go straight from Nightjar to Telegram.

ntfy push

Push notifications to your phone through ntfy.sh or your own ntfy server, no account required.

Webhooks

A JSON payload for anything else: PagerDuty, Opsgenie, or your own incident tooling. An optional shared-secret header lets your endpoint verify the sender.

05Operations

Pause and resume

Silence a check during maintenance without losing its history or its URL.

Rotate ping URLs

Generate a new token if a URL leaks into a public log. The old one stops working immediately.

Status badges

An SVG badge for your README or wiki that shows whether a job is passing. Pro and Scale.

Test sends

Fire a test alert at any channel and see the response code in a second or two.

05 Setup

If it can make an HTTP request, it can check in.

No agent, no SDK, no sidecar. One request at the end of the job, a second one at the start if you want timings. The highlighted line is the only change.
