Heartbeat monitoring for scheduled jobs

Your cron jobs fail quietly. Nightjar doesn't.

Add one line to the end of a backup, an invoice run or a nightly sync. If it doesn't check in on time, reports a failure, runs long or never finishes, you hear about it — with the last lines of its output in the alert.

01

Create a check

Name it and tell Nightjar when to expect it: every 15 minutes, or 0 2 * * * in Europe/Berlin. Add a grace period for jobs that run long on a busy night.

02

Ping it from the job

Append a request to the unique URL. Add /start to measure duration, /fail or an exit code to report errors, and POST the output to attach logs.

03

Sleep through the night

Nightjar watches the clock. When the ping doesn't arrive, it tells your Slack, Discord, Telegram or phone, then tells you again when the job recovers.

What it catches

Four ways a job goes wrong. One line catches all of them.

Missed

It didn't run at all

The server rebooted, someone edited the crontab, the scheduler was disabled. There's no error to log because nothing happened. Nightjar alerts on the silence.

Failed

It ran and broke

Report the exit code and POST the output. The alert arrives with the last lines of stderr attached, so you can see FATAL: password authentication failed without opening a terminal.

max 10m
Slow Pro

It ran three times longer than usual

Ping /start first and Nightjar records every run's duration. Set a maximum and get a warning when a run exceeds it, before slow turns into stuck.

Stuck Pro

It started and never finished

A deadlock, a hung network call, a lock that was never released. When a run has started but hasn't finished within its limit, you know while it's still happening.

Works with whatever runs your jobs

If it can make an HTTP request, it can check in.

Ping only when the job exits 0. -f makes curl fail on HTTP errors, --retry rides out network blips.

Questions

Fair questions.

More on the FAQ page and in the docs.

How does heartbeat monitoring work?

Each check gets a unique URL. Your job requests that URL when it finishes. Nightjar knows the schedule, so when a request doesn't arrive on time (plus a grace period you choose), the check goes down and you get an alert.

It catches the failures that log-based monitoring misses: the server was off, the crontab was overwritten, the container never started, or the job hung forever.

What does setup actually involve?

Create a check, copy its URL, and append one curl (or fetch, or wget) call to your job. There's no agent to install, no SDK, and nothing to run on your servers.

Can it tell me why a job failed?

Yes. Ping /fail or /<exit-code> and POST the job's output. Nightjar stores the tail of that output and includes it in the alert, so the Slack or Discord message already contains the error.

Which schedules are supported?

Simple periods (every 5 minutes, every 6 hours, every day) and standard 5-field cron expressions evaluated in any IANA time zone, so DST changes don't produce false alarms.

Where do alerts go?

Slack, Discord, Telegram, Google Chat, ntfy (push notifications to your phone, no account needed), and generic webhooks with an optional shared secret. Every channel can be tested from the dashboard.
